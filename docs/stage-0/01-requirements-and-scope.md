# 01 · 需求澄清与范围界定

## 1. 一句话定位

一个**多租户 OA 系统**，其审批核心不是「A 审完给 B 审」，而是
**「把审批拆成若干层，每一层由一组人同时投票，按可配置规则计票；每层通过后派发任务协同执行，任务完成再推动下一层；任何环节搞不定都可以按组织结构上报到上级部门」**。

## 2. 与传统逐级审批的差异

| 维度 | 传统单人逐级审批 | 本系统（层级多人投票制） |
| --- | --- | --- |
| 决策单元 | 一个人 = 一个节点 | 一层 = 一组投票人（可含权重） |
| 通过判定 | 该人同意即通过 | 按 `ALL / MAJORITY / RATIO / WEIGHTED / AT_LEAST_N` 计票 |
| 否决 | 该人驳回即驳回 | 可配 `ANY_VETO`（一票否决）或 `OPPOSE_OVER`（反对超阈值）或 `NONE` |
| 弃权 | 不适用 | 四选一策略：计入分母 / 不计入分母 / 视为同意 / 视为反对 |
| 超时 | 催办或挂起 | 四选一策略：仅提醒 / 自动通过 / 自动驳回 / 上报 |
| 执行环节 | 无（审批完就结束） | **任务引擎**：分配、协作、依赖、验收、逾期 |
| 僵局处理 | 无（线性流转不会僵局） | **上报引擎**：平票、连续驳回、超限、跨部门争议、任务阻塞都能上报 |
| 上级裁定方式 | 上级领导一人拍板 | **上报 = 在上级部门再跑一次同样的投票**：同一套计票规则、同样全员表态、同样人工结论，最终意见回写原流程 |
| 结果可复现性 | 依赖日志 | `VoteResult` 快照 + `InstanceNodeVoter` 投票人快照 + `AuditLog` |

## 3. 角色与职责

| 角色 | 关键职责 | 典型入口页面 |
| --- | --- | --- |
| 发起人 (Initiator) | 选模板填表发起、撤回、重新提交、查看进度 | 发起流程 / 我的流程 |
| 投票人 (Voter) | 在投票期内对某一层投票（同意/反对，**必须表态**）、附意见、查看**本部门**投票明细 | 投票中心 |
| 投票结论填写人 (Concluder) | 本层全员表态后，填写并提交该层的**人工投票结论**（确认或改判系统判定） | 投票详情 · 结论区 |
| 任务负责人 (Task Owner) | 接受/执行/提交验收任务，可转派 | 任务中心 / 任务详情 |
| 任务协作者 (Collaborator) | 参与任务、更新子任务或检查项 | 任务详情 |
| 任务验收人 (Acceptor) | 验收通过或打回 | 任务详情 |
| 上级部门处理人 (Escalation Handler) | 受理 / 退回 / 要求补充 / 发起上级投票 / 派任务 / 继续上报 / 终审 | 上报中心 / 上报详情 |
| 流程设计者 (Designer) | 维护模板、版本、节点、投票规则、任务模板、上报规则 | 流程设计器 |
| 组织管理员 (Org Admin) | 维护部门树、用户、角色、权限、数据范围 | 组织架构 / 角色权限 |
| 租户管理员 (Tenant Admin) | 全部权限（含系统配置、审计导出） | 全部 |
| 审计者 (Auditor) | 只读查看全量投票、上报链路、审计日志与导出 | 统计报表 / 审计日志 |

## 4. 端到端业务闭环（贯穿性场景，用于验收）

> 场景：某公司「采购金额 > 5 万的申请」需 **2 层投票 + 1 次任务执行 + 1 次上报**。

| 步骤 | 触发 | 系统行为 | 涉及引擎 |
| --- | --- | --- | --- |
| 1 | 业务员提交申请（amount = 80000） | 校验模板已发布版本；创建 `WorkflowInstance`；按 `NodeVoterRule` 解析第 1 层投票人（部门 3 人） | WorkflowService |
| 2 | 规则求值 `formData.amount > 50000` | 命中「需要第 2 层部门总监投票」分支；命中「金额超限需上报」标记 | RuleEngine |
| 3 | 第 1 层 3 人投票 | 3 人**全部表态**（默认无弃权）：2 同意 1 反对 → `MAJORITY` → 计票给出「拟通过」 | VoteEngine |
| 4 | 填写第 1 层投票结论 | 结论填写人填写「同意采购，需补充比价材料」并提交 → 节点 `PENDING_CONCLUSION → PASSED` | VoteConclusion |
| 5 | 第 1 层通过 | 按 `NodeTaskTemplate` 创建任务「补充三家供应商比价」，指派部门内负载最低者，24h 截止 | TaskEngine |
| 6 | 任务逾期未完成 | `task.overdue` 扫描命中；通知 + 规则命中「任务逾期 → 上报」 | BullMQ + EscalationEngine |
| 7 | 创建上报 | 沿 `Department.path` 上溯一层，目标 = **直接上级部门的工号**（不允许越级，也不投给个人）；流程进入 `ESCALATED` 并**冻结**（已确认）；生成 `EscalationChain` | EscalationEngine |
| 8 | 上级部门开投 | 通知该工号全部成员；默认投递即开投（`acceptMode=AUTO`）；**上级这一级也走同一套投票流程**（全员表态、不允许弃权、结论前可改票）；上级部门此时**可看到本流程全部层级的投票明细** | EscalationEngine + VoteEngine |
| 9 | 上级投票 + 上级结论 | 上级工号成员投票（如 3 人中 3 同意）→ 上级结论填写人填写「同意继续，需补充比价材料」→ 最终意见**回写原流程**；解冻并恢复冻结前状态 | VoteEngine + VoteConclusion + NodeStateMachine |
| 10 | 回到第 2 层投票 | 第 2 层 5 人全部表态，`RATIO 0.6 + 否决锁定`：4 同意 1 反对 → 4/5=0.8 ≥ 0.6，但否决规则锁定不予通过 → 结论人提交 **REJECTED** | VoteEngine + VoteConclusion |
| 11 | 流程驳回 | 通知发起人；流程 `REJECTED → CLOSED`；全过程留痕可导出 | AuditService |

该场景同时覆盖五条已确认规则：**全员必须表态且不允许弃权**、**不允许越级上报**、**统一投递到上级部门工号**、**上报 = 上级再投一次同样的票**、**上级部门可见全部投票明细**。

> 缺席处理不在主场景中，但属于必测分支：若第 1 层 3 人中有 1 人请假且未委托，则**投票池变为 2 人**，分母按 2 计算、阈值也按 2 计算（`MAJORITY` 下 2 人须 2 票同意才通过）；若池内人数低于 `minQuorum`（默认应投票人数的 60%），该层不得通过，直接转上报。

任何阶段交付后，都可用此场景做端到端回归。

## 5. 功能范围

### 5.1 范围内（In Scope）

| 域 | 能力 |
| --- | --- |
| 组织与权限 | 租户、部门树（物化路径）、用户、角色、权限、数据范围（本人/本部门/本部门及下级/指定部门/全租户） |
| 流程模板 | 模板 → 版本 → 节点/边 → 投票人规则、投票规则、任务模板、上报规则；发布与版本管理 |
| 流程实例 | 发起、撤回、重新提交、时间线、当前层、冻结/解冻 |
| 投票 | 投票人解析、投票（**必须表态，不允许弃权**）、**缺席处理（不算票、不计入投票池）**、计票（5 通过 + 3 否决规则 + 4 超时策略 + 最低法定人数）、**结论形成前可反复改票**、结果快照、催办、实时进度 |
| 投票可见性 | 投票人默认只能看到**本部门**投票明细；上级部门（上报链上的上级）可看到该上报相关的**全部**明细；跨部门仅展示聚合计数 |
| 投票结论 | 每层全员表态后由指定人**人工填写结论**（确认或改判系统判定），支持附件、理由与全程留痕 |
| 任务 | 主/子任务、检查项、依赖与阻塞解锁、指派（手动/角色/部门/投票组/负载均衡/抢单）、接受、执行、提交验收、验收通过/打回、转派、逾期扫描 |
| 上报 | 9 类触发源、目标投递（**仅直接上级与逐级上溯，不允许越级**，统一投给上级部门工号）；**上级处理 = 再跑一次同样的投票**（同计票规则、同全员表态、同人工结论）；结论含继续/退回/要求补充/终审，逐级上报直至形成结论 |
| 规则引擎 | JSON DSL：比较 / 逻辑 / 上下文路径；用于跳转、上报触发、任务分配、超时策略 |
| 实时与通知 | Socket.IO 房间与事件；站内 + 邮件 + 短信 + 企微/钉钉/飞书 Webhook |
| 审计与合规 | 全量写操作 before/after、投票不可改不可删、上报链路留痕、审计报表导出 |
| 统计 | 投票统计、节点耗时、任务统计、上报统计、人员负载 |
| 前端 | 18 个页面（见 02 文档），亮/暗主题，看板拖拽与甘特缩放 |
| 部署 | dev 一条命令；prod 一台机器 + 一个 compose；迁移 + 种子自动执行；备份/恢复脚本 |

### 5.2 范围外（Out of Scope，本版本不做）

| 项 | 说明 |
| --- | --- |
| K8s / 服务网格 / 多实例横向扩展 | 明确由用户约束排除；架构保留无状态化以便未来接入 |
| Nginx / Prometheus / Grafana | 同上；仅保留 `/health` 与 `/metrics` 端点 |
| 复杂 BPMN 2.0 全套语义（网关独占/包容、事件子流程、补偿） | 只实现 CONDITION 分支 + 投票/任务/上报四类节点，避免成为 BPM 引擎 |
| 可视化表单设计器（拖拽生成任意表单） | 本版本用「JSON Schema 表单 + 预制字段组件」，模板作者手写 schema，前端按 schema 渲染 |
| 电子签章 / CA 证书 / 手写签名法律效力 | 留出 `Attachment` 与审计接口，未来可扩展 |
| 财务/HR/ERP 深度集成 | 通过 Webhook + OpenAPI 双向，不做定制适配器 |
| 移动端原生 App | 只做响应式 Web（移动端可用），不含原生壳 |
| 越级上报 / 跳级指定部门 | 用户已确认**不允许**；代码保留开关默认关闭，不提供 UI 入口 |
| 投票「弃权」选项 | 用户已确认**不能弃权**，本版本不提供该选项；`AbstainPolicy` 枚举仅为历史数据兼容保留 |
| 上级单人裁定 / 上级独立派任务 | 用户已确认上级处理**必须走投票**，因此不做「领导一键终审」，也不做上级独立派任务；如需整改，由投票结论携带行动要求、回写后由原流程生成任务 |
| 全文检索（ES/OpenSearch） | 用 PostgreSQL `ILIKE` + 索引满足单机规模 |

## 6. 需求澄清清单（**请重点确认，尤其是 P0**）

> 每条给出「默认取值」，若不确认则按默认实现。P0 = 影响数据库/核心引擎，改起来贵；P1 = 影响接口或 UI，改起来便宜。

| 编号 | 问题 | 默认取值 | 级别 |
| --- | --- | --- | --- |
| Q1 | 投票可见性 | ✅ **已确认**：投票人**只能看到本部门**的投票明细；**上级部门能看到该上报相关的全部投票明细**；跨部门只展示聚合计数（已投数/同意数），不展示他人选择。实现为 `VoteViewScope=DEPT_ONLY`（默认）+ 上报链可见性覆盖 | P0 |
| Q2 | 是否允许改票 | ✅ **已确认**：**投票结论形成之前可以反复更改**（不限次数）；每次改票新增 `Vote` 行并把上一票标记 `isReplaced`，历史全留、计票只取最新；结论形成后（`PASSED/REJECTED`，或人工结论已提交）锁定 | P0 |
| Q3 | 平票（`MAJORITY` 且同意=反对）如何处理 | ✅ **已确认：报上级组织裁定**（`TiePolicy=ESCALATE`），上报目标 = 上级部门工号；`REJECT` / `CHAIRMAN_VOTE` 保留为可配项 | P0 |
| Q4 | `ALL` 规则遇到弃权票算不算通过 | ✅ **已确认：不能弃权**。投票只有同意/反对两种表态，本问题自然消解；`abstainPolicy` 保留但本版本不开放 | P0 |
| Q5 | 上报后原流程是否冻结 | ✅ **已确认：冻结**。流程进入 `ESCALATED`/`SUSPENDED`，计时暂停，投票与任务均不可操作；上级结论回写后解冻并恢复冻结前状态 | P0 |
| Q6 | 上报是否允许**越级** | ✅ **已确认：不允许**。`EscalationEngine` 只实现「直接上级 `DIRECT_PARENT`」与「逐级上溯 `LEVEL_UP`」；跳级（`SKIP_TO_LEVEL`）与「指定非直接上级部门」默认关闭，需租户级开关 `allowCrossLevel=true` 才启用，且启用后需 `ESC_CROSS_LEVEL` 权限 | P0 |
| Q7 | 截止时间是自然日还是工作日 | ✅ **已确认：自然日**（`DeadlineMode=CALENDAR_DAY`）。周末与节假日照常计时，因此**不需要**维护节假日日历 | P0 |
| Q8 | 投票人缺席（请假/出差）怎么处理 | ✅ **已确认：缺席不算票，也不计入总投票池**。缺席者从分母与权重中一并剔除（`N_pool = N_expected - absent`），既不触发催办也不算未表态；有委托（`Delegation`）时受托人投票代其行使、仍计入池内 | P0 |
| Q9 | 组织架构数据从哪来？ | 本版本**手工/API 维护** + 提供 CSV 导入；HR 系统同步留接口不做 | P1 |
| Q10 | 登录方式？ | 账号密码（JWT）+ 管理员重置密码；SSO/OIDC 与企微/钉钉扫码留扩展点不做 | P1 |
| Q11 | 任务是否有验收人强制要求？ | 是，每个任务必须有且仅有一个 `ACCEPTOR`（默认 = 派发人或其上级，可配） | P1 |
| Q12 | 附件上限与类型？ | 单文件 50MB，单任务合计 500MB；白名单扩展名；默认本地磁盘存储 | P1 |
| Q13 | 是否需要多语言？ | 不做 i18n 框架，但所有文案集中在 `packages/shared/messages`，便于后续替换 | P1 |
| Q14 | 时区与展示格式？ | 统一 `Asia/Shanghai`，数据库存 UTC `timestamptz`，前端按用户时区渲染 | P1 |
| Q15 | 审计日志保留多久？导出成什么格式？ | 默认保留 3 年，导出 CSV + JSON；不删除但支持归档表分区 | P1 |
| Q16 | 单租户还是多租户并行？ | 数据库全表带 `tenantId`（用户明确要求），但默认 seed 只建 1 个演示租户，UI 不做租户切换器 | P1 |
| Q17 | **人工投票结论由谁填写**？ | 默认 = **本部门工号的主责人**（`DepartmentWorkNoMember.isPrimary`）；该部门未配工号时回退到部门负责人（`isLeader=true`）；模板可改为「指定人 / 指定角色 / 上级部门处理人」。节点级配置 `conclusionAuthorRule` | P0 |
| Q18 | **人工结论与系统自动判定是什么关系**？ | 默认 `MANUAL_CONFIRM`：系统计票给出「拟通过 / 拟驳回」，填写人只能**确认或改判**，改判必须填理由并留痕；另两档 `AUTO`（系统判定即结论，不填）/ `MANUAL_OVERRIDE`（可自由改判） | P0 |
| Q19 | **全员必须表态**下，超时未表态怎么处理？ | 默认 `REMIND_ONLY`：催办最多 3 轮（间隔 8h），仍未表态则转 `ESCALATE` 上报上级部门。**`AUTO_APPROVE`（超时自动通过）默认禁用**（需租户开关 `allowAutoApprove`）——「必须表态」不能被静默代劳；`AUTO_REJECT` 可选 | P0 |
| Q20 | 「一票否决」与「全员必须表态」冲突吗？ | 默认不冲突：否决票**立即锁定本层不予通过**，但仍需等全员表态完成后才进入结论阶段（`vetoTerminates=false`）。若要求「一出现否决票立即终结投票」，把 `vetoTerminates` 设为 `true`，此时未表态者记为 `SKIPPED` | P0 |
| Q21 | 上级部门的接收方式与可见性范围 | ✅ **已确认**：每个部门配置**部门工号**（`Department.workNo`，租户内唯一），上报**统一投递到上级部门的工号**（不投给个人）。可见性范围 = 该实例上报链上的全部上级部门及其工号成员；非上报链上的同级部门**不可见** | P0 |
| Q22 | 一个部门是否只能有一个工号 | ✅ **已确认：按默认**，1 部门 = 1 工号（`Department.workNo` 租户内唯一） | P0 |
| Q23 | 工号成员范围与在上级投票中的角色 | ✅ **已确认**：工号成员**显式指定**；**工号成员即该级上报的投票人**（默认 `voterType=DEPT_WORKNO`，取目标工号成员，模板可覆盖） | P0 |
| Q24 | 上级处理方式 | ✅ **已确认：上级对下级的上报也必须投票**，投票流程与普通层完全一致（同一套计票规则、全员表态、不允许弃权、结论前可改票、人工填写结论），形成结论后**最终意见回写原流程**。不存在单人裁定；签收只是入口（`AUTO` 默认免签收） | P0 |
| Q25 | 上级投票「不通过」的默认回写动作 | ✅ **已确认：按默认 = `RETURN`**（退回原部门重走本层，给一次整改机会）；要终止流程需上级结论人显式选 `FINAL_REJECT` | P0 |
| Q26 | 上级投票的投票人 | ✅ **已确认：按默认** —— 上级投票人 = 目标工号**全体成员**（`voterType=DEPT_WORKNO`），权重默认 1，`isPrimary` 只决定"谁默认填结论"而非"谁才有票"；模板可覆盖为其他投票人规则 | P0 |

## 7. 非功能需求

| 类别 | 目标 | 实现手段 |
| --- | --- | --- |
| 性能 | 列表接口 P95 < 300ms（10 万实例量级）；计票写入 < 100ms | 组合索引 `(tenantId, status, deadline)`；计票在事务内单次聚合；Redis 缓存组织树与权限 |
| 并发 | 同一节点 200 人同时投票不丢票不重复 | `(instanceNodeId, voterId, isReplaced)` 唯一约束 + Redis 分布式锁 + 事务内条件更新 |
| 一致性 | 状态变更与事件投递最终一致 | Outbox 模式 + `outbox.dispatch` 重试 + 消费幂等（`eventId` 去重表） |
| 可用性 | 单机可跑；重启后队列任务不丢 | Redis AOF；BullMQ 延时任务持久化；启动时对账「超期未处理」节点 |
| 安全 | 密码哈希、令牌轮换、越权防护、上传安全 | argon2 密码；Access 15min + Refresh 7d（可吊销，Redis 存 jti 黑名单）；`PermissionGuard` + `DataScopeGuard`；上传白名单 + 落盘随机名 |
| 合规 | 投票不可篡改、链路完整可导出 | 投票表只 INSERT；`AuditLog` 记录 before/after 与 ip/ua；导出接口需审计权限 |
| 可观测 | 结构化日志 + 健康检查 + 指标 | pino JSON 到 stdout；`/health`（依赖探活）、`/metrics`（Prometheus 文本格式，但不部署采集器） |
| 备份 | 每日数据库备份 + 附件可打包 | `pnpm backup`（`pg_dump` 到挂载卷）/ `pnpm restore` |
| 可维护 | 类型不漂移、边界清晰、可测试 | monorepo 共享类型；领域服务纯函数化（计票/规则求值无 IO，便于单测） |
