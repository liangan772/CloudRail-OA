# 验收清单（阶段 6 第 7 步）

> 用真机 + 真数据逐条走。每条都能对应到一个**已经实现并测过**的能力，走不通就是真问题。

## A. 部署

- [ ] `docker compose -f docker/docker-compose.prod.yml up -d --build` 四个服务全部 healthy
- [ ] `curl localhost:3001/health` → `status=ok`、`dependencies.database=up`
- [ ] `pnpm db:seed` 成功（或确认已灌过种子）
- [ ] `GET /jobs/status` → `mode=queue`（有 Redis）或 `in-process`，`outbox.pending=0`
- [ ] `pnpm backup` 产出 `docker/backups/oa-*.dump`

## B. 登录与权限

- [ ] 打开前端域名 → 跳转 `/login`
- [ ] `admin@cloudrail.dev / Oa@12345678` 登录成功，工作台显示数据范围 TENANT
- [ ] 故意输错密码 5 次 → 提示账号锁定（15 分钟）
- [ ] 用只有 VOTE_READ 的账号访问 `/templates` → 显示"缺少哪些权限点"的说明页

## C. 主流程（采购申请：两层投票 + 任务 + 金额超限上报）

- [ ] 王强发起（金额 1.2 万）→ 首层投票人 = 技术部 4 人，通知到达
- [ ] 技术部 4 人投票 → 投到最后一票自动进入"待填写结论"
- [ ] 王强（工号 D1003 主责人）填写结论通过 → **派出任务并挂起**（第 1 层不推进）
- [ ] 负责人接单 → 勾完 3 个检查项 → 提交验收（检查项没勾完时按钮是禁用的）
- [ ] 验收人通过 → 本层任务全部完成 → **自动开启第二层**（产品中心工号 3 人）
- [ ] 技术部的人看第二层进度 → 只看到聚合计数（跨部门）；产品中心的人能看到姓名
- [ ] 李静（D1001 主责人）填结论 → 流程停在"已通过"（不自动归档）

## D. 上报链路

- [ ] 发起金额 8 万的流程 → 全员表态后**不直接出结论**，而是建上报单并冻结流程
- [ ] 上报单投递到 `D1001`，产品中心 3 名工号成员收到通知
- [ ] 上级按同样规则投票（3 人）→ 进入"待上级填结论"
- [ ] 李静填 `CONTINUE` → 原流程**解冻恢复投票**；填 `RETURN` → 回到原层重走（轮次 +1）
- [ ] `POST /escalations/:id/upgrade` 能逐级上溯到总部 `D1000`

## E. 设计器

- [ ] 模板页草稿版本 →「去设计」→ 能看到整图 JSON
- [ ] 「校验」通过；故意删掉 END 或投票规则 → 校验报出具体问题
- [ ] 「保存」成功；「发布」后在模板列表看到新版本已发布，旧版本被锁定
- [ ] 已发布版本打开设计器 → 保存/发布按钮不可用（要求先克隆草稿）

## F. 实时与通知

- [ ] 两个浏览器分别登录投票人与发起人，投票后对方页面收到实时事件
- [ ] `/notifications` 有未读、可标记已读、可跳转来源
- [ ] 配了 IM Webhook 时，通知摘要能推到群里；Webhook 挂掉不影响站内通知

## G. 数据与运维

- [ ] 审计日志有记录（`select action, count(*) from audit_logs group by 1`）
- [ ] Outbox 无积压（SENT 占绝大多数，DEAD 为 0）
- [ ] `pnpm --filter @oa/api db:cleanup` 预演能列出流程数据，`--yes` 后清空且组织/模板仍在
- [ ] 上线前执行运维手册 §6 的审计分区 SQL，并确认新分区按月自动创建

## H. 已知未做（验收时不算缺陷，但要知道）

- 流程设计器是 JSON 式编辑，没有拖拽画布
- 统计只有指标卡与任务分布，没有时间趋势图
- 邮件/短信渠道未接（站内通知 + IM Webhook 已通）
- 登出是无状态实现（服务端不保存刷新令牌，无法主动吊销设备）
